# Datasets

The datasets behind the prototype. Start here if you have not seen them before.

## Read this first

**Every figure in every file here is invented.** Costs, user counts, utilisation, scores,
risks, dates, owners, contract terms — all made up. The only real things are the
**product and vendor names** (Epic, Workday, ServiceNow and so on) and the public
capability descriptions taken from vendor product pages.

Both portfolios are **fictional organisations**. Nothing here comes from a client, and no
client-supplied file may ever be added to this directory — see `.gitignore` at the
repository root. There is no patient data and no protected health information. Person
names appearing as application owners or SMEs are invented; in the Northstar files they
are literally suffixed `(synthetic)` and their email addresses use the reserved
`.example` domain, so they cannot resolve to anyone.

Nothing here is a benchmark. Do not quote a number out of these files as a fact about any
real organisation.

## Two portfolios, three directories

| Directory | What it holds |
| --- | --- |
| `synthetic-portfolio/` | The team's own 20-application dataset, generated by `engine/generate_dataset.py`. This is the portfolio the wireframe is built around. |
| `client-intake/` | The same dataset narrowed to only the columns a client would supply, plus the intake paperwork describing what we ask for and what we work out ourselves. |
| `northstar/` | A second, separately built 20-application sample — "Northstar Global Health" — and the three runs that scored it through the engine. Built by hand as an independent test of the model, not generated by the engine. |

## `synthetic-portfolio/` — the team's dataset

| File | What it is |
| --- | --- |
| `App-Rationalization-Dummy-Dataset-v2.xlsx` | **Current.** 20 applications, 126 columns, 8 sheets. Uses the agreed five-term vocabulary (retain, invest, consolidate, replace, retire). Generated output. |

| `CHANGELOG-v2.md` | What changed between v1 and v2 and why, including the three applications whose recommendation moved. Read this before comparing the two versions. |

## `client-intake/` — what the client is asked for

| File | What it is |
| --- | --- |
| `Client-Input-Dataset-v1.xlsx` | **Current.** The v2 dataset projected down to the 57 client-supplied columns, with a blank template sheet and a round-trip check. Generated output. |

## `northstar/` — the second portfolio and its scoring runs

Inputs — hand-built sample workbooks, **not** generated by anything in this repository:

| File | What it is |
| --- | --- |
| `healthcare_app_rationalization_sample_20.xlsx` | **Input.** The original Northstar sample: 20 applications across 11 sheets (inventory, users, capabilities, risks, TCO, dependencies, performance). |
| `healthcare_app_rationalization_sample_20-with-risk.xlsx` | **Input.** The revised sample, adding a `Healthcare Guardrails` sheet. Runs 2 and 3 read this one. |

Outputs — produced by running those inputs through the engine:

| File | What it is |
| --- | --- |
| `Northstar-Disposition-Analysis-v3.xlsx` + `northstar-dispositions-v3.csv` | **Current.** Run 3. Use these for any current number. |
| `Northstar-Disposition-Analysis-v2.xlsx` + `northstar-dispositions-v2.csv` | **Superseded.** Run 2, which promoted risk to a gated dimension. |
| `Northstar-Disposition-Analysis-v1.xlsx` + `northstar-dispositions.csv` | **Superseded.** Run 1, the first pass. |
| `scoring-model-review.md` | A review of the scoring weights: what they are, and whether re-weighting would change any recommendation. Analysis, not output of a run. |

The superseded runs are kept on purpose — each workbook carries a "What changed" sheet, and
the progression from v1 to v3 is how the model was arrived at.

## Inputs versus generated files

Inputs — nothing in this repository produces them:

- `northstar/healthcare_app_rationalization_sample_20.xlsx`
- `northstar/healthcare_app_rationalization_sample_20-with-risk.xlsx`
- `client-intake/column-tiers.json`

**Generated outputs**, reproducible by the scripts in `engine/` — the six versioned
workbooks and their six CSVs, plus `CHANGELOG-v2.md`, which the generator emits alongside
the dataset. `engine/README.md` lists which script writes which file and the paths each one
expects. One exception: the superseded `App-Rationalization-Dummy-Dataset-v1.xlsx` /
`applications.csv` came from an earlier revision of the generator that is not committed, so
today's `generate_dataset.py` reproduces v2, not v1.

Written by hand: `client-intake-requirements.md`, `scoring-model-review.md`, and
`client-intake-checklist.xlsx`.

If you regenerate a workbook, expect it to match the committed one. If it does not, the
committed file is the one whose numbers were checked.
